## Task 0 — the page fights the scroll (blocking, do this first)

Theodor: "when you come down to the second track, you can't scroll to it, it's
lagging up all the time."

This is a real bug and it is already diagnosed. Measured in headless Chrome at
1440×900 on 2026-07-28:

- Sitting still in §02, the page scrolled itself **−797px** in 1.5 s, on 4 scroll
  events the reader did not cause.
- Scrolling down 260px at a time, 26 notches: two of them lost **−1704px** and
  **−1665px**, and **10 of 26 notches lost ground**.

**Cause** — in `js/main.js`, the entry IntersectionObserver ends with:

```js
const chip = chips.find(c => c.dataset.key === key);
if (chip) chip.scrollIntoView({ behavior: 'smooth', block: 'nearest', inline: 'center' });
```

`.chips` is a **sticky, horizontally scrollable** bar. `scrollIntoView` walks *every*
scrollable ancestor, including the document, so centring a chip drags the page
vertically → that re-fires the observer → which centres the next chip → loop.
`behavior: 'smooth'` makes it a slow animation that actively fights the reader's
own scrolling.

**Fix** — move the bar's own `scrollLeft` and nothing else. Setting `scrollLeft`, or
calling `scrollTo` on the container element, cannot touch the document scroll:

```js
const centreChip = (chip) => {
  const bar = chip.parentElement;                 // .chips
  const target = chip.offsetLeft - (bar.clientWidth - chip.offsetWidth) / 2;
  const max = bar.scrollWidth - bar.clientWidth;
  bar.scrollTo({ left: Math.max(0, Math.min(max, target)), behavior: 'smooth' });
};
```

Then audit **every other** `scrollIntoView` in the codebase for the same trap. The
chip *click* handler in `renderChips()` uses it deliberately to jump to an entry —
that one is fine, it is user-initiated — but check it does not race the observer.

**Regression test** — add to `trace/verify.mjs`, both of these:

- Land in §02, sit still 1.5 s, assert `|scrollY drift| < 4px`.
- Scroll down in 260px steps 26 times, assert every step moves ≈260px (allow ±30)
  and that no step goes backwards.

Without these two checks the bug will return the next time something is added to
that observer.

## Task 1 — it runs at 5 fps

Theodor: "it's a bit laggy when you scroll."

Measured 5–6 fps at every scroll position (headless software rendering, so his
machine is faster — but that is nowhere near 60 on real hardware either).

Three canvases each repaint fully every frame, and nothing is gated on visibility.

**The globe is the biggest cost.** Per frame it:
- re-projects all **5 123 land points** across 126 rings, doing fresh
  `sin`/`cos` per point, then `fill()` **and** `stroke()` per ring;
- re-projects the graticule (~1 375 more points);
- fills **four full-disc radial gradients** — halo, ocean, terminator, rim — over a
  ~660px disc.

Fix in this order, measuring after each so you know what actually paid:

1. **Cache the rotation-independent layers.** Halo, ocean, terminator, rim and limb
   do not depend on `state.lon`/`state.lat` at all — only on size and theme. Render
   them once into two offscreen canvases ("below land" = halo + ocean, "above
   graticule" = terminator + rim + limb) and `drawImage` them each frame. Invalidate
   on resize and on theme change. This should be the single biggest win.
2. **Precompute the per-point trig.** A point's latitude never changes, so its
   `sin`/`cos` never change — only its longitude relative to the camera does. Build
   a flat `Float64Array` of `[lonRad, sinLat, cosLat]` per ring once at module load
   and read from it in `project()`. Removes about two thirds of the trig.
3. **Gate on visibility.** The circuit figure in §03 runs even when it is nowhere
   near the viewport — put an IntersectionObserver on `.figure` and pause it. The
   globe fades to ~0.14 opacity past the hero; below some threshold, stop painting
   it or drop it to ~15 fps.
4. **Decimate when small.** `ringPath` already takes a `step`; widen it as the
   rendered radius shrinks, and skip rings whose whole extent is under a few pixels.

There is already a `pause()`/`resume()` pair on all three canvases wired to
`visibilitychange` — reuse that plumbing rather than inventing a second one.

**Add an fps floor to `trace/verify.mjs`**: measure at the hero, in §02 and in §03,
and fail under 30 fps. Note in the test that headless is slower than real hardware,
so 30 is the floor, not the target.

## Task 2 — the globe should read as a big globe

Theodor says it "needs to look like a big globe" and that there are visual bugs, but
has not said which ones. **Do not guess and start changing things.** Reproduce
first, show him, then fix what he confirms.

Reproduce: `node trace/shots.mjs`, plus extra frames at 1920×1080, 2560×1440, and a
short-and-wide viewport (1600×700). Crop in on the globe. Put them in front of him
and ask which artifacts he means.

Things that are genuinely suspect, so check these specifically:

- **Horizon seams.** `ringPath()` draws runs of consecutive *visible* points and
  simply skips the rest. There is no true horizon clipping, so a landmass crossing
  the limb gets a straight chord drawn across it instead of following the edge. At
  small sizes this is sub-pixel; at 2560 it will be obvious.
- **Coastline resolution.** The data is Natural Earth **110m** — deliberately coarse.
  On a 1200px globe the coastlines will look faceted. If he wants crisper, move to
  50m; `trace/extract.py` already decodes topojson, so it is a data swap plus a size
  check, not new code. It will cost frame time — do Task 1 first.
- **Lakes fill as land.** The topojson decode emits every ring separately, so interior
  rings (Caspian, Great Lakes) are filled as land rather than punched out. Fix by
  building proper `Path2D` polygons with holes and letting the even-odd/nonzero rule
  do the work.
- **Antarctica.** In land-110m it is a clipped polygon, not a closed continent. Near
  the south limb it can draw as a band across the disc.
- **The terminator is not a real terminator.** It is an offset radial gradient, so it
  reads as a soft blob rather than a day/night great circle. At large sizes this is
  probably the thing that stops it looking like a lit sphere. Consider computing an
  actual sub-solar point and shading by the dot product of the surface normal with
  the sun vector — that is what makes a sphere look spherical.
- **Size on wide-short screens.** `#globe-wrap` is `88vmin`, so on 1600×700 `vmin` is
  height-driven and the globe shrinks to ~616px while the page is 1600 wide. If
  "big" means "big", this sizing is probably the actual complaint. Consider
  `min(88vmin, 62vw)` or driving it from `vw` with a height clamp.

Whatever changes, `#scrim` must keep the body copy legible over it in both themes,
and the day-side opacity rule in `assets/app.css` must still hold.

## A correction to make out loud first

Theodor asked for "the same files as the first project — standalone-src, the
`.dc.html`, all of those". Those exist in 1.x because 1.x was authored as a
**single-file Claude artifact**: `Field Atlas (standalone-src).dc.html` is the
editable master, `Field Atlas.dc.html` is the same with the thumbnail stripped, and
`index.html` is the bundler's output with `support.js` (the artifact runtime)
substituted in. That chain is a property of the authoring tool, not of the app, and
2.0 has no such runtime.

| Field Atlas 1.x | Field Atlas 2.0 |
|---|---|
| `Field Atlas (standalone-src).dc.html` — editable master | `index.html` + `assets/` + `js/` + `data/` — the editable master |
| `Field Atlas.dc.html` — derived | *(nothing — no artifact runtime)* |
| `index.html` — bundled single file, what Pages serves | `dist/index.html` — bundled single file, what Pages serves |
| `support.js` — artifact runtime | *(nothing — plain ES modules, inlined)* |
| `sw.js`, `manifest.webmanifest`, `.nojekyll`, `icons/`, `fonts/` | **the same — build these** |

Say this in a sentence or two, then proceed. Do not create empty `.dc.html` files to
match the 1.x listing.
